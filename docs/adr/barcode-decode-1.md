# barcode-decode-1: Apple Vision (roster-clamped) is the iOS barcode DECODE engine

Status: accepted.

## Context

Android decodes still images with pure-JVM ZXing inside a zero-permission `isolatedProcess` (`:barcodeDecoder`) guarded by a watchdog `ProcessKiller`, so the main process never runs a native image codec on them; its live-camera path decodes pure-JVM ZXing in-process (Android ADR 0008). iOS has neither ZXing nor an isolated-UID child process to contain a native codec, and the kernel's other barcode surface is encode only (`PassesCore/BarcodeMatrix`, `ScannableFormat`, `PassesUI/BarcodeView`; see `passes-ui-1`, `passes-ui-2`).

## Decision

`PassesBarcode` decodes with Apple Vision (`VNDetectBarcodesRequest`), clamped by an allowlist. `RosterSymbology.requested` is the only place the roster is defined: `[.qr, .code128, .ean13, .code39, .aztec, .pdf417]`, pinned by `requestedAllowlistIsExactlyTheRosterSymbologies`. DataMatrix stays out deliberately, as on Android: it widens the same surface for no reported need.

A Swift ZXing/ZXingCpp port was rejected: it would bring the native-codec attack surface Android spends an isolated process containing into the app's own address space. Vision adds no third-party dependency, is reported to decode out of process in system services (the closest iOS analogue to Android's sandbox), and keeps one Apple-imaging story alongside the CoreImage encode path. A ZXing port is re-escalatable only as a separate security decision.

UPC-A has no `VNBarcodeSymbology`: Vision reports it as EAN-13 with a leading zero, and `RosterSymbology.fold` maps that to `.upcA` with the 12-digit payload, the same classification ZXing produces, so scans of one physical card agree across platforms. The Aztec and PDF417 members exist because boarding passes arrive as screenshots with no pkpass to carry them. Wider allowlists enlarge both the hostile-image parser surface and the misread-ambiguity risk; this is accepted (Android Threat 14 analogue) because a boarding-pass screenshot otherwise decodes to nothing, bounded by the roster clamp, the bounded still-image decode, the faithful-payload posture and the app-side confirm-before-create gate.

## Deviations from Android

1. **Different binarizer.** Vision's binarizer is not ZXing's, so fidelity on adversarial or degraded inputs differs. The `HostilePayloadFidelity` corpus is re-baselined against Vision, not assumed to carry over. All corpus payloads (RTL override, zero-width and control chars, Cyrillic homoglyph not NFC/NFKC-normalized, actionable schemes, SQL metacharacters, newline/tab, oversize) round-trip verbatim.
2. **The `isolatedProcess` containment claim is dropped.** iOS cannot spawn an isolated-UID child, so decoding in a killable sandbox process does not port. Compensating controls:
   - Roster clamp (`VNDetectBarcodesRequest.symbologies`) limits the parser surface to the roster.
   - Bounded `CGImageSource` decode: byte-size, per-side-dimension and megapixel caps enforced from the image header before any bitmap is allocated (decompression-bomb / CVE-2023-4863 libwebp-class guard).
   - A timeout wrapping the decode, the analogue of Android's `ProcessKiller`. It bounds the caller's wait only: Vision `perform` is synchronous and non-cancellable, so a hung decode is orphaned, not killed.
   - Label-never-autofilled spoof guard: the decoder returns the payload faithfully and never interprets or acts on it; classification and validation stay in the consumer (`QrPayloadKind` / `ScannableCardInputValidator`).
   - Walt-wide residual protection: on-device-only data, no network egress from the decode path.
3. **A `.data` source arm is allowed.** Android forbids a `ByteArray` source because it would mean the hostile image already sits in the main-process heap, defeating its isolation. iOS has no such premise, and `PHPicker` yields either in-memory `Data` or a temporary file `URL`.
4. **The live-frame boundary is a `CVPixelBuffer` (K12), not Android's `ByteArray` plus Y-plane geometry.** Vision ingests a `CVPixelBuffer` natively, including the camera's biplanar YUV, so a byte-shaped entry would force rebuilding a pixel buffer and discard Vision's plane handling. `CVPixelBuffer` is CoreVideo, not AVFoundation: the capture glue (`AVCaptureVideoDataOutput` to `CMSampleBuffer` to `CMSampleBufferGetImageBuffer`) stays app-side (A8). The kernel receives a bare frame snapshot plus a `CGImagePropertyOrientation`, which subsumes Android's `reverseHorizontal` flag and carries rotation. Both paths share one Vision core (`VisionSymbolDecode`) and one roster. The live path skips the bounded still-image decode, since a frame is already-decoded app-owned pixels; the roster clamp, faithful-payload posture and timeout carry over.

## Decode timeout and lane banks

`withDecodeTimeout` runs the decode on dedicated serial `DispatchQueue` lanes owned by `PassesBarcode`, and schedules the deadline on a separate owned lane. Running the decode on the Swift cooperative pool let a caller that parks the pool's threads (for example `SignatureVerifier.runBlocking`'s `semaphore.wait()`) keep the decode from starting while the deadline fired on schedule, so the guard measured thread availability rather than decode duration. With the pool parked, work submitted via `Task.detached`, a concurrent `DispatchQueue` or `DispatchQueue.global` had not begun after 20 s; a dedicated serial queue began in 0.1 ms. Only dedicated serial lanes are immune, since concurrent and global queues draw from the pool the cooperative pool exhausts.

- **Two banks.** `DecodeBank.stillImage` (untrusted files from the share sheet or picker) and `.liveFrame` (app-captured camera frames) are separate `DecodeLanes` instances with their own lanes, overflow ceiling and accounting, so wedging the still-image path cannot consume a slot the scanner needs.
- **Sizing.** 8 lanes plus a 32-thread overflow per bank (`decodeLaneCount`, `decodeMaxOverflowThreads`), at most 80 live decode threads across both banks reached through `DecodeBank` (tests build smaller banks outside it). Width follows in-flight decodes rather than cores, since Vision is reported to decode out of process and a lane waits on that service. `theBanksCannotOutgrowTheirDocumentedThreadCeiling` asserts the total across `DecodeBank.allCases`.
- **A decode never queues behind another.** A free lane is reused; when all are occupied the work spills to a transient thread (`spillsOnlyUntilTheCeiling`); past the ceiling the bank refuses and drops the work, releasing its payload. Queueing is gone because it reproduced false `decodeTimedOut` results (an instant operation losing a 5 s race purely by queueing), and an unbounded queue retains each payload (a `CGImage` up to ~50 MP or a camera `CVPixelBuffer`) behind a lane a wedged decode never releases. Lane occupancy is therefore a flag; `refusesRatherThanQueueingOntoAnOccupiedLane` pins the property that flag depends on. Queueing must not return without a depth count.
- **A refusal is not resolved early.** The caller waits its full budget and then gets `decodeTimedOut` from the already scheduled deadline, because `FrameScanLoop` (the consumer's scan loop, not in this repo) clears its in-flight gate on each result and would otherwise spin at camera rate against a bank that cannot recover. Each refused caller still holds its own payload until its deadline (5 s), so retention past the cap is bounded by the budget times the number of concurrent callers, which the app bounds: the scan loop runs one decode at a time and imports are user-driven one at a time.
- **Which decodes hold a slot.** A decode that returns an answer, including a failure answer such as `noBarcodeFound`, releases its slot in a `defer`. A decode that overruns its budget resolves the caller with `decodeTimedOut`, keeps running and releases its slot when it finishes. Only a decode that never returns, because Vision `perform` cannot be cancelled, holds its slot for the life of the process. Occupancy accumulates only from that third case, which needs a crafted input that hangs Apple's decoder.
- **Residual saturation.** About 40 wedged decodes per bank (8 lanes plus 32 overflow) saturate it for the life of the process; the live-frame path has no other bank's capacity to fall back on. Every later decode is refused and surfaces as `decodeTimedOut`, whose contract ("the same input may decode fine later") is misleading in that state. Reporting saturation as a distinct arm was declined: it needs a public enum change plus consumer copy and would add an iOS-only arm, for a state reachable only by inputs that each hang Apple's decoder. Revisit if saturation is ever observed in the wild.
- **Residual delivery.** This fixes which executor the decode runs on, not that resuming the caller needs the caller's own executor; if the caller's pool is blocked it observes the result late. `decodeNeverRunsOnTheCooperativePool` pins that the decode runs on a context this module owns.
- **Still-image scope.** The still-image facade runs the whole pipeline, the ImageIO codec step and the Vision read, inside the bounded wait on this bank. The only check outside it is the I/O-free `.data` byte cap. A wedging codec burns a lane slot rather than a cooperative-pool thread.

Test seams: placement is a value type (`LanePlacement`), pinned deterministically at two lanes and a ceiling of one in `LanePlacementTests`. `withDecodeTimeout` has an overload taking a `DecodeLanes`, so `LaneBankIsolationTests` builds one-lane, no-overflow banks and reaches a full bank with a single holder, covering refusal, isolation and the wiring (`DecodeLanes.bank(.stillImage) !== DecodeLanes.bank(.liveFrame)`) without a thread storm. Saturating a real bank is not used as a gate: "40 holders must start" asserts something about the runner and fails on correct code. `decodeDoesNotQueueBehindSaturatedLanes` holds slots in the real still-image bank, which sibling suites also draw from, and refusal makes over-subscription a hard failure, so any test against the production banks must leave real headroom.

## Failure taxonomy

`DecodeFailureReason.decodeTimedOut` separates the timeout from `decoderUnavailable` (a Vision `perform` failure). They call for opposite responses: an unavailable decoder will not succeed on retry, a timed-out one is a load signal. Conflating them already cost a misdiagnosis of timeouts as an absent Vision framework. `expiredBudgetReportsDecodeTimedOut` on each decoder pins the arm.

Android has the same arm by a different mechanism. Its `DecodeWatchdog` runs inside the isolated process and expires by `killer.killSelf()`, so the sandbox cannot report its own timeout. `BarcodeDecodeClient` therefore attributes a binder dropped at or past the budget to `DecodeTimedOut` by elapsed time, and folds an earlier drop, a `false` `transact` and any malformed reply into `DecoderUnavailable`. The kernels mirror each other's contracts (result shape, roster clamp, faithful-payload posture); how each populates an arm may diverge where process models do.

## Aztec and PDF417

- **Decode-only mechanism.** `ScannableFormatConstraints.decodeOnly` is read by the validator (refuses to mint a card as `unsupportedFormat`) and by `ScannableFormat.isCreatable()` (filters consumer pickers); the encoder's exhaustive switch is the encode-side guard. The set is empty and remains for a future decode-first addition.
- **Confirmation gate.** `requiresCreateConfirmation(format:)` keys off `ScannableFormat.canCarryActionablePayload()` (QR, PDF417, Aztec true; 1D false), so an actionable Aztec/PDF417 payload gets the same create-time confirmation as QR. This is a consumer obligation: the kernel supplies the predicate, and the gate holds only if the app calls it rather than a copy.
- **Pinned encode parameters (CoreImage):** Aztec `inputCorrectionLevel` 33 (spec recommendation; CoreImage's default is 23), PDF417 level 3 (ISO/IEC 15438's recommendation at boarding-pass codeword counts). Compaction and margins stay on CoreImage defaults; measured PDF417 aspect is 2.7-3.5:1, from which the 320 x 90 render floor derives.
- **Latin-1 charset.** Vision decodes ECI-less Aztec and PDF417 bytes as ISO-8859-1, so UTF-8-encoded "café" would scan back as "cafÃ©" on the app's own decoder. CoreImage exposes no ECI control, so the encoder emits ISO-8859-1 bytes (verified round-trip verbatim, high-Latin-1 included) and the validator admits only Latin-1-representable characters for these two formats, using the same `data(using: .isoLatin1)` conversion as the encoder. Deviation from Android, which accepts full Unicode via ZXing's ECI: a CJK-payload Aztec/PDF417 card cannot be created (`wrongCharset` at typing time); scanning one created elsewhere still works, since its ECI declaration travels with the symbol. QR keeps UTF-8 (`passes-ui-2`).
- **Payload caps.** `ScannableFormatConstraints` caps PDF417 at 800 and Aztec at 1,500 characters. Measured against the live generators at the pins, Aztec holds 2,674 single-byte characters and PDF417 1,823, so under the Latin-1 posture a cap-length payload always encodes (`writersEncodeAtTheFullCap`). An IATA BCBP payload runs about 60 characters per leg. Raising either EC pin (above PDF417 level 3 or Aztec 33%) shrinks capacity and requires re-deriving the caps; `writersEncodeAtTheFullCap` fails if a cap-length payload stops encoding.
- **No multi-scale rescale ladder.** Android needed one because ZXing is single-scale; Vision detects at multiple scales, and a ~3000 px screenshot-scale Aztec decodes directly (`largeScreenshotScaleDecodesWithoutARescaleLadder`).
- **Roster width is free on the live path.** Vision measured ~4.3 ms per no-symbol 720p frame with six symbologies and ~4.4 ms with four on an M-series Mac, because Vision's detection stage dominates. Measured on a Mac; absolute iPhone numbers are higher, and the roster-width delta is what this measures.

## Consequences

The app-side decode routing, camera, image-import and share work reuses this roster clamp and result mapping. The app's camera privacy string and Share-Extension entitlement are separate sign-offs, not resolved here.
